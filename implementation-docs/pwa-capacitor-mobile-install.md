# Plan: Installable mobile app on Android + iOS (PWA hardening + Capacitor native wrap)

> Generated by `/brainstorm` on 2026-08-12. Working notes at `notes/pwa-capacitor-mobile-install/`.

## Frame

- **Kind**: feature (packaging/distribution, not app-logic)
- **Files/modules likely touched**: `index.html`, `public/manifest.json`, `public/sw.js`, `public/icons/*.png` (new), `vite.config.ts`, `package.json`, `capacitor.config.ts` (new), `android/` + `ios/` (new, generated), `src/lib/notifications/notifier.ts`, `src/lib/notifications/adapter.ts` (new), `src/lib/notifications/adapter.test.ts` (new), `src/main.ts`

- **Out of scope**: public App Store / Play Store listing and review; remote/push notifications (local/scheduled only, matching current behavior); backend changes (Supabase sync, opt-in, untouched); CI-based native builds (native builds are manual/local — user confirmed they have a Mac and will build via Xcode directly)

## Research summary

- Current PWA is incomplete, not absent: `public/manifest.json:11-18` has a single SVG icon marked `"purpose": "any maskable"` — Chrome installability requires separate 192×192 and 512×512 icon entries, and combining `"any maskable"` in one entry is against spec guidance ([web.dev: Web app manifest](https://web.dev/learn/pwa/web-app-manifest), [Chrome DevTools installable-manifest](https://developer.chrome.com/docs/lighthouse/pwa/installable-manifest)).
- `index.html:1-15` has no `apple-touch-icon` or `apple-mobile-web-app-*` meta tags — iOS Safari doesn't read the web manifest for home-screen icon/standalone behavior, it needs these directly. Missing them means "Add to Home Screen" screenshots the live page and may not launch standalone.
- `vite.config.ts:8` hardcodes `base: '/palan/'` for GH Pages; `src/lib/notifications/notifier.ts:19` hardcodes `navigator.serviceWorker.register('/palan/sw.js')`; `public/manifest.json:5-6` hardcodes `start_url`/`scope` to `/palan/`. Capacitor native WebViews load from `capacitor://localhost` / `https://localhost` at webroot `/`, not `/palan/` — a hardcoded GH-Pages base would 404 every asset inside the native shell. Capacitor's documented pattern is `base: './'` for the web build it consumes ([Capacitor docs](https://capacitorjs.com/docs), via [OtaKit guide](https://www.otakit.app/blog/vite-app-to-ios-android-with-capacitor)).
- `src/lib/notifications/notifier.ts:6-24` already gates on `'Notification' in window` and no-ops gracefully when absent — won't crash inside Capacitor, but means zero reminders fire natively today, since iOS WKWebView never exposes `Notification`. README's own "Platform Limitations" section (`README.md:136-140`) already documents this as a known, accepted gap in the pure-PWA path.
- `public/sw.js:1-58` is a hand-rolled cache-first SW with a `periodicsync` handler and version-based cache eviction (`CACHE_NAME` bump on `activate` deletes stale caches, `public/sw.js:13-20`) — not relevant inside Capacitor (native ships bundled assets already); should only register in the plain-browser context.
- `.github/workflows/*.yml` only builds+deploys the GH Pages web build today; no Android/iOS CI job exists (and none is being added per confirmed scope).
- `@capacitor/local-notifications` schedules via `at`/`on`/`every` with a `repeats` flag; Android 12+ needs `SCHEDULE_EXACT_ALARM` in the manifest for exact-time delivery, Doze-mode delivery needs `allowWhileIdle: true` ([Capacitor Local Notifications docs](https://capacitorjs.com/docs/apis/local-notifications)). iOS additionally caps pending local notifications at 64 per app (`UNUserNotificationCenter`, general iOS platform constraint) — not documented in the codebase, surfaced during plan review.

## Approaches considered

### Approach 1: Single web build, env-conditional base + runtime platform branch (only approach proposed — see rationale below)

- **Scope**: Fix PWA installability gaps (icons, iOS meta tags, manifest) as a prerequisite shared by both the web and native targets. Add Capacitor on top of the _same_ `src/` tree — no forked entry point. `vite.config.ts` reads an env var (e.g. `BUILD_TARGET=capacitor`) to switch `base` between `/palan/` (GH Pages) and `./` (Capacitor webDir). Notification delivery is extracted behind an explicit adapter interface (`src/lib/notifications/adapter.ts`) with a web implementation (existing SW + `Notification` API path, untouched) and a native implementation (`@capacitor/local-notifications`), selected via `Capacitor.isNativePlatform()`.
- **Sequencing**: spike first — `npx cap add android` / `npx cap add ios` against the env-conditional `base: './'` build, confirm it actually launches on a device/emulator — before any icon/manifest/adapter work lands on top of it.
- **Files/modules**: `vite.config.ts` (env-conditional base); `package.json` (new `build:capacitor`, `cap:sync`, `cap:android`, `cap:ios` scripts + Capacitor deps); new `capacitor.config.ts`; `index.html` (add `apple-touch-icon`, `apple-mobile-web-app-*` meta); `public/manifest.json` (split `any`/`maskable` icon entries, add 192/512 PNGs); new `public/icons/*.png` (generated from `favicon.svg` via `@capacitor/assets` or `sharp`); new `src/lib/notifications/adapter.ts` (interface: `scheduleReminders(plants, settings)` / `cancelAll()` / `syncScheduledNotifications()`, web + native implementations); `src/lib/notifications/notifier.ts` (calls the adapter instead of branching inline; `syncScheduledNotifications()` invoked from every mutation that currently triggers `checkAndNotify` — mute toggle, quiet-hours edit, care action logged, plant added/removed); new `src/lib/notifications/adapter.test.ts` (unit tests against both branches, `Capacitor.isNativePlatform()` mocked); `src/main.ts` (skip SW registration when `Capacitor.isNativePlatform()`); `public/sw.js` (bump `CACHE_NAME` alongside the hardening change, using the SW's existing version-based eviction as the rollback mechanism); small Settings-page status line showing SW-registration state / last-successful-schedule timestamp; new `android/` + `ios/` native project dirs (generated by `npx cap add`); no CI changes — native builds stay manual/local.
- **Key risks**:
  - Runtime platform branching means the untested notification path can silently regress — mitigated by the extracted adapter interface + unit tests against both branches as a real done-criterion.
  - `@capacitor/local-notifications` schedules are OS-queued ahead of time and don't re-evaluate quiet-hours/mute state on their own — `syncScheduledNotifications()` must run on every state change affecting `checkAndNotify`'s output (all four trigger points), or reminders go stale.
  - Android 12+ needs `SCHEDULE_EXACT_ALARM` in `AndroidManifest.xml` for exact-time delivery.
  - iOS caps pending local notifications at 64 — schedule only a rolling near-term window (bundled next-due-per-day, capped ~14 days ahead) rather than one-per-plant-per-schedule-type.
  - Accepted, unsolved limitation: if a user ever runs both the browser-installed PWA and the sideloaded native app on the same device, each schedules independently with no dedup — not solved now (single hobby user, one install path in practice).
- **Complexity**: medium. Icon/manifest/meta-tag fixes are small and mechanical; Capacitor scaffolding is one-time setup with platform-specific fiddling (signing config, permissions); the notification adapter + reschedule-trigger wiring is the one real app-logic change and the biggest source of correctness risk.
- **Why no alternative approach is proposed**: a forked entry point (duplicate `main.ts`, duplicate `vite.config`) was considered and ruled out — it isolates native-vs-web code cleanly but duplicates the entire route tree and component wiring for no functional gain, since Capacitor's own recommended pattern is exactly "one web app, runtime platform checks" via `Capacitor.isNativePlatform()`. Single-build-with-branching also means future bug fixes and features land in both targets automatically instead of needing to be ported twice.

## 4 Shapes (from the develop-perspective review sub-agent)

- **Nature**: Single-organism-with-adaptive-phenotype is the right shape — one `src/` tree branching by environment, not two forked organisms. The plan correctly uses two different decision moments (build-time env var for the static `base`, runtime check for notification delivery) matching when each fact actually becomes knowable.
- **Domain**: The "same event will be retried/duplicated, plan for it" instinct wasn't originally applied to the multi-install-surface case (PWA + native on one device) — flagged, and explicitly accepted as an unsolved edge case at this scale rather than folded in.
- **Theory**: The right abstraction is a port/adapter (one interface, two implementations) — originally only implied in risk prose, not scoped as actual files/tests. Now corrected: `adapter.ts` + `adapter.test.ts` are explicit deliverables.
- **Implementation**: A spike (`cap add` + `cap sync` against the env-conditional build, confirmed launching) should happen before building anything on top of it, since Capacitor's file-origin sensitivity is easy to get subtly wrong and expensive to discover late.
- **Tensions**: Theory (OS-scheduled notifications are fire-and-forget once queued) vs. Domain (existing bundling logic implies near-delivery-time evaluation of mute/quiet-hours state) — resolved by making `syncScheduledNotifications()` an explicit, required call from every state-mutation path, not an implied side effect.

## Picked Reliability Tenets (from the reliability-tenets review sub-agent)

- **Tenet 3 (reduce blast radius)**: shared code path between existing web-PWA users and new native users means a notification regression from wiring up Capacitor could affect people who never touch Capacitor — mitigated by making the adapter+tests a real gate, not an aspiration.
- **Tenet 6 (staggered rollout + rollback)**: web-side manifest/SW hardening ships to 100% of installed PWA users at once via the existing static deploy — full staged-rollout infra is disproportionate at this scale; the cheap mitigation folded in is bumping `CACHE_NAME` so the SW's existing version-based eviction acts as the rollback path.
- **Tenet 4 (automated anomaly detection)**: both SW-registration failure and native notification-scheduling failure fail silently on-device, in an app whose entire value proposition is timely reminders — mitigated with a minimal Settings-page status line rather than a telemetry stack.

- **DEFER (partial)** — No staged rollout/rollback for web-side SW/manifest changes — full staging infra is disproportionate for a single-user personal deploy; cheap partial mitigation folded in: bump `CACHE_NAME` on the hardening change so the SW's existing version-based eviction handles rollback.

## Pre-mortem

- **Most likely failure**: the native build looks fine (icons, install experience correct) but reminders silently drift from reality — a user mutes a plant or edits quiet hours, `syncScheduledNotifications()` isn't wired into that specific mutation path (easy to wire 3 of 4 trigger points and miss one), so a stale native schedule fires an incorrect reminder with no error surfaced anywhere.
- **Rollback**: web side — `git revert` the manifest/icon/SW commit, push to `master`, existing GH Pages Actions workflow redeploys; the SW's own `CACHE_NAME`-based eviction (`public/sw.js:13-20`) means already-installed clients pick up the revert on next SW activate, no migration needed. Native side — no installed base to roll back (sideload-only, single device); fix the adapter bug, `npx cap sync`, rebuild in Xcode/Android Studio, reinstall over the existing app (Capacitor preserves app data across same-bundle-id reinstall).
- **Detection + responder**: Settings-page "last successful notification schedule" timestamp is the visible signal; responder is the single developer/user (personal app, no on-call) checking manually. The adapter unit tests covering all four reschedule trigger points are the real first line of defense — they catch a missed wiring point at review time rather than relying on the indicator being noticed later.

## Recommendation

Single web build with an env-conditional Vite `base` and a runtime `Capacitor.isNativePlatform()` branch, gated behind an explicit notification adapter interface with tests for both branches. This is the only approach proposed — the forked-entry-point alternative was ruled out as pure duplication for no functional gain. Main tradeoff: the shared-codebase choice means a notification bug can affect both web and native users at once, which is why the adapter/test extraction was elevated from "aspiration" to "required deliverable" during review. The user can redirect on: the iOS 64-notification-cap mitigation strategy (rolling window vs. some other capping scheme), or revisit the deferred PWA+native dedup question if dual-install ever actually happens.
